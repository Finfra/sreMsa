# 콜드 스타트 — 첫 요청만 유독 느린 이유

* 서버리스에서 **첫 호출이 느리고 두 번째부터 빨라지는 현상**을 직접 재어 봅니다.
* 강의 자료의 콜드 스타트 그림(`환경 기동 → 런타임 초기화 → 내 코드 실행`)을 숫자로 확인하는 실습입니다.

* **먼저 알아 둘 것 — 이 실습의 OpenFaaS CE 에는 "0 으로 줄이기"가 없습니다.**
    - AWS Lambda 같은 관리형 FaaS 는 요청이 없으면 인스턴스를 **0 개까지** 내렸다가, 요청이 오면 그때 띄웁니다. 그래서 콜드 스타트가 생깁니다.
    - OpenFaaS 는 그 기능(scale to zero)이 **Pro 전용**입니다. CE 는 **최소 1개**를 유지합니다. 실제로 `kubectl scale --replicas=0` 을 걸어도 오퍼레이터가 즉시 1로 되돌립니다.
    - 그래서 여기서는 **파드를 지우고 다시 뜨는 구간**을 재어 같은 현상을 봅니다. 원리는 같습니다 — *"실행할 인스턴스가 없는 상태에서 요청이 오면 무슨 일이 벌어지는가"* 입니다.

## 1. 준비 [vm01에서 실행]

```
export OPENFAAS_URL=http://192.168.56.11:31112
faas-cli store deploy nodeinfo
sleep 30
faas-cli list
```

## 2. 웜(warm) 상태의 응답 시간 — 기준선 [vm01에서 실행]

* 이미 떠 있는 함수를 세 번 부릅니다.

```
for i in 1 2 3; do
  curl -o /dev/null -s -w "호출$i: %{time_total}s (HTTP %{http_code})\n" $OPENFAAS_URL/function/nodeinfo
done
```

* 확인 : 첫 줄만 조금 크고 이후는 밀리초 단위입니다.
```
호출1: 0.157035s (HTTP 200)
호출2: 0.005239s (HTTP 200)
호출3: 0.004865s (HTTP 200)
```

* cf) 여기서 이미 30배 차이가 납니다. 이것은 콜드 스타트가 아니라 연결·캐시가 데워지는 구간입니다. 진짜 콜드 스타트는 다음 단계에서 봅니다.

## 3. 인스턴스를 없애고 다시 부르기 [vm01에서 실행]

* 창을 하나 더 열어 파드 상태를 지켜보면 이해가 빠릅니다.

```
kubectl get pods -n openfaas-fn -w
```

* 원래 창에서 파드를 지우고, 곧바로 1초 간격으로 호출합니다.

```
kubectl delete pod -n openfaas-fn -l faas_function=nodeinfo --wait=false

for i in $(seq 1 10); do
  curl -o /dev/null -s -w "  HTTP %{http_code}  %{time_total}s\n" --max-time 30 $OPENFAAS_URL/function/nodeinfo
  sleep 1
done
```

* 확인 : **세 단계가 순서대로 나타납니다.**
```
  HTTP 503  0.002640s     ← ① 실행할 인스턴스가 없다 (즉시 거절)
  HTTP 200  4.023089s     ← ② 파드가 뜨는 동안 요청이 대기 (콜드 스타트)
  HTTP 200  0.004800s     ← ③ 웜 (이후 계속 빠름)
```

* **① 503 과 ② 4초가 이 실습의 핵심입니다.**
    - ① 은 *"인스턴스가 없으면 요청이 그냥 실패할 수도 있다"* 는 사실입니다.
    - ② 의 **4.02초**가 곧 `환경 기동 + 런타임 초기화` 비용입니다. 웜 상태(0.005초)와 비교하면 **약 800배**입니다.
    - 대고객 API 에서 이 4초가 어디에 떨어지느냐가 SLA 를 가릅니다.

* cf) 숫자는 환경마다 다릅니다. 중요한 것은 **자릿수 차이**이지 4.02 라는 값이 아닙니다.

## 4. 왜 느린가 — 어디서 시간이 가는지 보기 [vm01에서 실행]

```
kubectl get events -n openfaas-fn --sort-by=.lastTimestamp | tail -8
```

* 확인 : `Scheduled` → `Pulled` → `Created` → `Started` 순서가 보입니다. 이 네 단계의 합이 콜드 스타트입니다.
* cf) 이미지를 이미 받아 둔 노드에 뜨면 `Pulled` 가 빨라집니다. **콜드 스타트 시간이 매번 같지 않은 이유**가 이것입니다.

## 5. 완화책을 생각해 보기

* 강의에서 다룬 완화책이 여기서 어떻게 대응되는지 짚어 봅니다.

| 강의의 완화책 | 이 환경에서 대응되는 것 |
| :--- | :--- |
| 최소 인스턴스 상시 유지 | CE 는 최소 1을 유지 — 사실상 이 상태가 기본값입니다 |
| 패키지 경량화 | 함수 이미지 크기를 줄이면 `Pulled` 단계가 짧아집니다 |
| 초기화 코드를 핸들러 밖으로 | 핸들러 밖 초기화는 파드당 1회, 안쪽은 요청마다 실행됩니다 |
